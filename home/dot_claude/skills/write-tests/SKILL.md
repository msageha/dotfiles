# Writing Tests

The tests rule (`~/.claude/rules/tests.md`) decides the level a test is written at, what it may assert, where it goes and when to use test doubles; read it before step 1 if it is not in context, with the rule for the language of the test files. This skill is the order of work for a request to write tests. Whether to add tests, harnesses and dependencies follows AGENTS.md and the request.

## Steps

1. Scope: take the features, entry points or paths the argument names (`$ARGUMENTS`; when it is empty or not substituted, the request text). A request that names nothing (「テストを実装して」) covers the features users use through each of the project's entry points.
2. Contract: collect what the tests protect from sources other than the code under test: the expected results the request itself states, README and docs, specifications and design docs, API schemas (e.g. OpenAPI), CLI help, the documentation and declarations of the public interface itself (docstrings, types), how existing callers use the code, and issues or bug reports that settle the current behavior (a proposal for a change is not a guarantee of the current version). For each feature in scope, list the results it guarantees in normal, error and boundary cases. Where they disagree (unless the request settles it) or leave a result open, report it as an open question instead of asserting it (a result you can only infer from the implementation is open), and go on with the results they settle. When no result in scope is settled, report the missing specification and the paths it leaves open before setting anything up.
3. Entry points: find how users call each feature (HTTP or RPC endpoints, CLI commands, a UI, a job or queue consumer, the exported API of a library) and how a test can call it with what the project already has (the web framework's test client, the CLI run as a subprocess, the app started in-process). Find the existing boundaries where a dependency the tests cannot control or must not reach (an external service, an LLM or agent CLI, the clock) can be replaced.
   - Set up what the tests need to run as the rule's Level item describes for a request to write tests, and document the test command where the project documents its other commands. Only when the public API still cannot be called that way, follow the rule's fallback for the missing harness.
4. Plan: when the tests use `@playwright/test`, also read the playwright skill where available. For each feature, choose scenarios by the rule's Coverage item and fix the level of each: the level the user named, or the public API unless the rule's Level item gives a reason for a lower one, in which case write the reason down for the report. Decide where each test goes by the rule's Placement item.
5. Write: drive the operation under test through the interface under test and take each expected result from step 2. Set up preconditions through that interface, another supported entry point or an existing fixture that produces a state real use can reach, or, for a dependency the tests cannot control, a test double at the boundary found in step 3 (the rule's Test Doubles item); not by patching internals or writing internal state directly. Put setup that several tests share (signing in, creating a record, starting the app) in fixtures or helpers, so that a change behind the interface touches no test.
6. Check:
   - Before each run, confirm that the tests run the code in the tree under test and write only to test-local data (e.g. a server the test configuration reuses must run this tree's code against test data, not a shared database). Run the new tests and the existing suite with the project's test command. When a new test fails on the unchanged code because the code breaks the contract (not because of setup or the test itself), keep the expected result, report the input, the expected and the actual result, and fix the code only when the request covers it. That failure already shows the test catches the violation, so the violation check below can skip it.
   - Confirm that a test catches a violation of what it protects for a representative scenario of each contract whose violation would cost users most, and for scenarios whose assertions you cannot tell by reading would catch one; run only those tests. Run the test against a version that breaks the contract for that scenario's input: the code before a known bug fix when one exists, otherwise a change you make (e.g. return a wrong value, skip a required check) after confirming it really alters the result for that input. Do this in a disposable copy of the working tree that includes the new tests (e.g. copied to a temporary directory), with a process started from the copy rather than a reused server; run the test there once before the change and confirm it passes, so that a failure afterwards comes from the change and not from the copy. Do it only when the tests there run that version's code (rebuilt first if the entry point runs a built artifact) and touch no shared state (an installed artifact, an already running server, a real home directory or database); otherwise, or when rebuilding and starting the system for it costs more than the check is worth, report the check as not done instead of editing a working tree someone else may use. The test must fail because of the violation (its assertion, or an error the contract does not allow), not at setup; when it still passes, fix its input or assertions until it does.
   - Read each test as if the code behind its interface had been refactored without changing the contract (internal modules renamed or moved, functions split or merged, internal call order changed). A test that would have to change imports, patches or asserts on internals: rewrite it through the interface under test, unless it is a lower-level test the rule allows and what it depends on is that part's own interface.
   - Finally, run the project's usual test command on the code and tests you deliver and confirm that it collects and runs the new tests (a run from the first bullet counts when nothing changed since). When you changed the runner's configuration, also confirm that the tests it ran before still run, by comparing the collected tests and failures with a run before the change.
7. Report: the scenarios per feature and their level (with the reason for any test below the public API), the commands and their results, the parts of the public path the tests leave unverified, the open questions from step 2, and the missing harnesses or tools you propose instead of adding.

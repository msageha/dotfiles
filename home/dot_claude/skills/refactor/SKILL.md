# リファクタリング

引数 (`$ARGUMENTS`。空または置換されない場合は依頼文) で指定されたファイル・シンボルをリファクタリングする。

## Goal

対象コードを、外部から観測可能な振る舞いを保ったまま、より読みやすく保守しやすい状態にする。

## Acceptance criteria

- 既存テストの結果がリファクタリング前と変わらない (自分の変更で検査として意味を失って消したテストは除き、消したものを報告する)
- テストが無ければ、止まらずに lint / build / 型検査など既存の検証手段で確かめ、テストが無いことを完了報告に書く
- 1 commit にまとまるサイズに収まっている
- 最終レポートに、何をどう変えたかと、変更前後の検証結果 (コマンドと件数) を含む

## Constraints

- 外部から観測可能な振る舞いを変更しない
- 次のいずれかに該当する場合だけ、変更の適用前にユーザーの承認を取る:
  - 公開 API のシグネチャ変更を伴う
  - スコープが 1 commit に収まらず分割が必要 (分割計画を示す)
  - 既存テストの削除 (変更で検査として意味を失ったものを除く。AGENTS.md「検証と完了」)、または期待値・検証対象の仕様を変える修正が必要 (rename・import path・シグネチャの機械的な追従は範囲内)
  - 依存パッケージの追加・削除を伴う
- それ以外は委譲の範囲として、計画・適用・テストの再実行・結果の報告まで続けて行う

## 手順

1. 対象コードと、その呼び出し元・既存テストを読み、責務と変更の影響範囲をつかむ。どこをどう変えるかは AGENTS.md「コード」の基準で決める。
2. Constraints の承認対象に当たるときは、変更の対象・変更概要・リスク (破壊的変更の可能性と対策) を計画としてユーザーに示す。
3. 変更の前に既存テスト (無ければ lint / build / 型検査など) を実行し、その結果を変更後と比べる基準にする。
4. 変更を適用して同じ検証を再実行し、結果が基準から変わっていないことを確かめる。

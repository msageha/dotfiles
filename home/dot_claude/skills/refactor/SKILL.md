# リファクタリング

引数 (`$ARGUMENTS`。空または置換されない場合は依頼文) で指定されたファイル・シンボルをリファクタリングする。

## Goal

対象コードを、外部から観測可能な振る舞いを保ったまま、より読みやすく保守しやすい状態にする。

## Acceptance criteria

- 既存テストの結果がリファクタリング前と変わらない (自分の変更で検査として意味を失って消したテストは除き、消したものを報告する)
- テストが無いか対象の振る舞いを覆っていなければ、止まらずに lint / build / 型検査など既存の検証手段と手順 4 の前後比較で確かめ、テストが覆っていない範囲と未検証の経路を完了報告に書く
- 1 commit にまとまるサイズに収まっている
- 最終レポートに、何をどう変えたかと、変更前後の検証結果 (コマンドと件数) を含む

## Constraints

- 外部から観測可能な振る舞いを変更しない
- 次のいずれかに該当する場合だけ、変更の適用前にユーザーの承認を取る:
  - 公開 API のシグネチャ変更を伴う
  - スコープが 1 commit に収まらず分割が必要 (分割計画を示す)
  - 既存テストの削除 (変更で検査として意味を失ったものを除く。AGENTS.md「検証と完了」)、または期待値・検証対象の仕様を変える修正が必要 (rename・import path・シグネチャの機械的な追従は範囲内)
  - 依存パッケージの追加・削除を伴う
- それ以外は委譲の範囲として、計画・適用・テストの再実行・結果の報告まで続けて行う

## 手順

1. 対象コードと、その呼び出し元・既存テストを読み、責務と変更の影響範囲をつかむ。どこをどう変えるかは AGENTS.md「コード」の基準で決める。
2. Constraints の承認対象に当たるときは、変更の対象・変更概要・リスク (破壊的変更の可能性と対策) を計画としてユーザーに示す。
3. 変更の前に、変更が及ぶ利用者の経路 (CLI の起動・API のリクエスト・画面の操作等、入口から出口まで) と、そこで保つべき観測結果 (出力・exit code・例外・書き込まれた状態) を挙げ、それぞれを入口から確かめる既存のテストを対応づける。内部の関数だけを確かめるテストは、入口の引数処理や起動経路を覆わない。既存テスト (無ければ lint / build / 型検査など) を実行し、その結果を変更後と比べる基準にする。
   - 各検証がどの版の実装を実行するかを確かめる。build・install・apply 等で反映した成果物を検査するものは、変更の前後それぞれで使い捨ての環境へ反映してから回し、反映できなければ未検証として扱う。
4. 既存テストが入口から確かめていない経路と観測結果は、対象を変更の前後で実行して比べる前後比較で確かめ、その結果も基準に加える。
   - 利用者が通る入口 (CLI・REPL・ローカルの API へのリクエスト・ブラウザ等) から、既存の手段でその場で実行する。リポジトリにテストや検証スクリプトを足さない (足すのは AGENTS.md「検証と完了」が認めるときだけ)。
   - 正常・境界・異常の経路を、同じ入力と同じ初期状態から使い捨ての環境 (一時ディレクトリ・既存の dry-run 等) で実行し、比べる出力は一時ディレクトリに置く。dry-run が書き込みを省くなら、書き込まれる状態は未検証として扱う。
   - 制御できる入力 (時刻・乱数の seed 等) は揃える。実行ごとに変わる値 (生成 ID・時刻等) は契約が定める性質 (形式・一意性・ほかの出力や保存先との参照関係) で比べ、順序が契約に無い出力は各値の出現回数まで含めて並べ替えてから比べる。
   - secret を出しうる経路は、AGENTS.md「安全」に従ってダミーの値で実行するか、出力をマスクしてから保存して比べる。外部への送信や共有の状態の変更を伴うなど、安全に実行できない経路は実行せず、未検証として報告する。
5. 変更は 1 つの変換 (関数の抽出・移動・rename 等) ずつ適用し、そのたびに変換が触れる範囲の検証を回す。壊れたときに、原因を直前の変換に絞れるようにするため。全ての変換を終えたら、手順 3・4 と同じ検証を同じ入力と初期状態で回して基準と比べる (最後の変換の後の検証が、手順 3・4 と同じ範囲を同じ入力と初期状態で確かめていれば、その結果を使う)。

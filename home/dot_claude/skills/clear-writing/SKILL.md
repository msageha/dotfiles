# 説明文の書き方

目的は、内容を知らない読み手が一度読んで正しく理解できる文章にすること。
AI が書いた文章に多い定型句や画一的な構成は、要点を埋もれさせるので避ける。
ただし、AI が書いたと見破られないこと自体は目的にせず、そのために文の長さや語り口を変えない。変えると、内容より書き方が目立つ。

対象は、依頼された成果物として渡す、人が読む数段落以上の日本語の説明文 (報告書・PR 本文・issue・docs・設計書・記事と、チャットで渡すそれらの原稿)。
ユーザー自身に宛てた質問への回答や作業の報告・コードと、エージェントの振る舞いを定める指示文 (AGENTS.md・skill・プロンプト) は対象にしない。
依頼・テンプレート・ほかの skill (documentation-writer・design-doc・pr 等) が内容・順序・見出し・列挙の形を指定していれば、それに従い、この skill はその中の文の書き方に当てる。

## 書く前に決める

- 読み手が誰かと、読み手に伝えることを、自分のために一文にまとめる (文書に載せる必要はない)。依頼に書かれていなければ、原文・既存の資料・コードから決める。それでも成果物の方向が変わるほど決まらないときだけユーザーに確認し、ほかは根拠のある推定で進める。
- 読み手の判断や操作に要る事実 (手順の前提・条件・数値等) を確かめられなければ、推測で埋めず、確かめられた部分まで書いて、何が足りないかをユーザーに伝える。
- 見出しには、その節の結論か扱う対象を書き、見出しだけを順に読めば内容の流れが分かるようにする (「背景」「について」だけで済ませない)。結論に条件が付く節では、条件を落とした結論を見出しにしない。条件も含めて短く書けるならそうし (「管理者だけが申請を承認できる」)、収まらなければ扱う対象を見出しにする。条件の消えた見出しは本文より強い主張として読まれる。
- 節や段落の長さは、読み手にとっての重要さと説明に要る量で決め、それが違う節を同じ文数・同じ構成にそろえない。そろえると、読み手は重要な箇所と軽い箇所を区別できない。

## 説明を組み立ててから短くする

- 先に、隣の読み手に口頭で説明するつもりで、何がどうなり、なぜ、どんな場合かを組み立てる。そのうえで重複・前置き・回りくどい修飾を削り、主体・動作・因果・比較対象・条件は残す。語だけを削った文は、読み手が意味を補わないと読めない。
- 削っても長すぎるなら、語を削り続けず、主題から外れる話題や重複する補足を省くか、別の節へ移す。読み手に要る情報は省かない。
- 結論から書く。冒頭に、主題の理解に要らない一般論・時代背景・「本稿では〜を解説する」のような予告を置かない。結論を理解するのに要る背景は残す。
- 抽象的な語や「〜の実現に寄与する」のような名詞を連ねた言い方のせいで、その文だけでは誰が何をするか、どの条件で何が起きるかが分からないなら、実際に起きることとその条件に書き直す。書き直す内容は、資料・コード・原文で確かめたものに限る。確かめられないなら、元の語のまま残すか、何を確かめれば書けるかを伝える。分野の標準用語は言い換えず、要るなら説明を添える。
- 書き手が思いついたたとえや呼び名のうち、読み手が何を指すか特定できないものは、対象の名前か実際の動作で書く。読み手が知らないと考えられる専門用語は、初出で何をするものかを短く添える。

## 文と段落の組み立て

- 仕組み・利用条件・例外・注意点が一文に詰まって読みにくければ文を分け、一文には主張を一つだけ置く。条件は、それがかかる文や表のセルの近くに置く (「管理者に限り削除できる」のように短い条件は同じ文に置く)。
- 項目に分けると因果が見えにくくなる箇所は、文でつないで関係を明示する。箇条書きにすると項目どうしの「だから」「しかし」が消え、関係を読み手が補うことになる。箇条書きは、読み手が手順を追う・項目を比べる・項目を個別に参照するときに使い、一文にそうした項目が詰め込まれていれば箇条書きにする。一続きの説明を「太字の語: 説明」の箇条書きに分けない。
- 強調 (太字・「非常に」「極めて」) は、文書全体で本当に目立たせたい箇所に限る。どこにでも置くと、どこも目立たなくなる。
- 二重否定と、否定を含む条件のせいで真偽や適用範囲を追いにくい文は、意味が同じになる肯定形に書き直す。明快な禁止や例外の否定はそのままにする。書き換えたら、真偽・適用範囲 (未設定などの第三の状態を含むか)・例外・主張の強さと、文脈から読み取れる含みが原文と同じかを確かめ、同じにできない否定は残す。
- 読み手が抱いていない誤解を打ち消す文 (「〜を意味するわけではありません」) や、言い換え・強調のためだけの「〜ではなく〜」の対比を書かず、何であるか・何が起きるかを書く。読み手の判断に要る否定 (禁止・例外・できないこと・誤解されやすい点・違いの説明等) は否定形で書く。
- 主張を問いかけの形 (「〜ではないだろうか」) で書かず、主張として書く。推量や異論の余地を含む問いなら、その不確かさを「〜と考える」「〜の可能性がある」のように残す。
- 名詞の前に長い修飾を重ねず、述語を持つ文に書き直して、頭から順に読める語順にする。修飾語は修飾する語の近くに置き、主語と述語を離さない。
- 「の」が続いてどの語にかかるかを追いにくい句、長く続く漢字の塊、硬い指示語 (「当該」「上記」) は、助詞や動詞を使った言い方に書き直す。「することができる」は「できる」にする。
- 対比・限定・根拠を担わない前置きや留保 (「〜という観点において」「重要なのは」「基本的に」) は外す。
- 確信の度合いは根拠に合わせて書き分ける。断定できることは断定し、推定・未確認はそうと書く。読み手の判断が変わる箇所では、確かめた事実か、決まったことか、提案かも分かるように書く。語尾の「〜と思われます」を全体に散らすと、どこが確かなのかが分からなくなる。
- ダッシュやスラッシュで文をつながず、読点・句点で区切る。本文で読む必要がある条件や説明を括弧に入れない。括弧の中は読み飛ばされやすい。

## 見直す

- 完成した文章だけを、内容を知らない読み手として読む。何の話で何が起きるかが分かるか、隣り合う文で話題が飛んでいないか、同じものを別の語で呼んでいないかを確かめる。
- 「これ」「その処理」のような指示語が指すものと、受け身や主語の省略で隠れた行為者が、文脈から一つに決まるかを確かめる。決まらなければ、確かめた根拠に基づいて書き足す。表現だけを直す依頼では、書き足すのは原文から一つに決まるものだけにし、コードや資料で見つけた事実は本文に足さずにユーザーに伝える。根拠が見つからないときは推測で補わず、確認が要る点としてユーザーに伝える。
- 同じ条件・数値・用語が本文・表・図・注記の複数箇所に出るなら、どこも一致しているかを確かめる。
- 引っかかる箇所は、語の置き換えを繰り返さず、説明の組み立てに戻って直す。短くして意味が落ちた箇所には、必要な語を戻す。
- 同じ書き出しの文や同じ構成の段落が並んで、要点や論理の関係が見えにくくなっていたら、内容に合わせて文をまとめるか、順序や主語を変える。比較やリファレンスのように、構成をそろえることで読みやすくなっている箇所はそのままにする。単調さを崩すためだけに疑問形・体言止め・短い文を差し込まない。

## 既存の文章の表現を直すとき

表現だけを直す依頼では、ほかの節の規範を、この節の制約を破らない範囲で当てる。内容を更新する依頼 (仕様の変更を README に反映する、PR 本文を最新の差分に合わせる等) では、依頼の範囲と確かめた根拠に従って内容を変え、表現にはこの skill のほかの節を当てる。

- 元の文章にある事実・条件・理由・数値は残す。削ってよいのは、重複と、何も伝えない前置き・枠付け・強調だけ。長すぎても話題は減らさない。
- 元の文章に無い事実・数値・条件・評価・意見を足さず、確信の度合い (推定・予定・合意) も変えない。直した文章は書き手の言葉として読まれるので、足した内容は書き手が言っていないことになる。足してよいのは、原文で指す意味が一つに決まる略語や用語の正式名称・短い定義と、元の文章から一つに決まる文どうしの関係・行為者・指示語の指すものだけ。仕様や数値の追加が要ると気づいたら、本文に足さずにユーザーに伝える。
- 節の構成と順序は、依頼が求めない限り変えない。元から読みやすい文と、意味の変わらない好みの言い換えには手を付けない。文体 (です・ます / である) と語り口は元に合わせる。
- コード・コマンド・識別子・数値・引用は原文のまま残す。
- 直し終えたら元の文章と並べ、元に無い内容が入っていないか、元の情報が抜けていないか、否定や条件の意味が変わっていないかを確かめる。

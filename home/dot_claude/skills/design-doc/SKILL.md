# 設計文書 (要件定義書・Design Doc)

引数 (`$ARGUMENTS`。空または置換されない場合は依頼文) が示す変更について、実装前の文書を書く。

## Goal

人間が短時間でレビューして判断でき、承認後は LLM エージェントがこの文書とリポジトリだけを見て、問い返さずに実装できる文書にする。

- レビューする人: 会話を見ておらず、前提知識が無い。読むのは、判断すべき点と、それが正しく書かれているか。
- 実装するエージェント: 文書に書かれたことを書かれたとおりに受け取り、書かれていないことはコードと自分の規約から決める。曖昧な語は推測で埋め、例の値はそのまま写し、範囲外と書かれていない隣の機能は足しがちである。

## 文書の種類

- 要件定義書: 何を・なぜ作るか。利用者から見た振る舞い・範囲・受け入れ条件を書き、実現方法は書かない。人の判断が要る設計の分岐が残るなら、実装に渡す前に Design Doc かユーザーへの確認で決める。
- Design Doc: どう作るか。構成・データ・外部との契約・判断の理由を書く。要件定義書があれば参照し、無ければ要件を冒頭に短く書く。
- 依頼された種類の文書を書く。両方を頼まれたときは、1 つの文書にまとめ、要件と設計をレビューする人や時期が違うときだけ分ける。

## 手順

1. 依頼・関連するコードと既存の文書を読み、リポジトリで確かめられる事実 (現状の構成・既存の仕組み・使える依存) は確かめてから書く。
2. 文書が決めるべき判断のうち、依頼と既存の資料で決まらないものを洗い出す。
   - 方向が変わる判断は、ユーザーに 1 回にまとめて確認する (AGENTS.md「依頼の解釈」)。答えを待つ間は、文書の「未決事項」に選択肢と推奨を添えて書き、決まったら本文に反映して未決事項から消す。
   - それ以外は推奨を採って該当する節に書く。軽微な判断は文書に書かず、作業の報告に書く。
   - 実現できるか分からない点は、設計を決める前に小さく試して確かめる。
   - 実装するエージェントは問い返せないことがあるので、実装に渡す版には、その文書で決めるべき判断を未決のまま残さない。
3. 下の「書くこと」から要る節だけを選んで書く。
4. レビューする人として読み直し、判断すべき点がすぐ見つかるか、前提知識なしで読めるかを確かめる。次に実装するエージェントとして読み直し、読み方によって利用者から見た結果・外部との契約・人が決めるべき判断が変わる箇所を直す。それ以外の実装の選び方は、実装するエージェントに任せる。独立レビューは AGENTS.md「検証と完了」「委譲」に従い、レビューする側には、文書・対象のリポジトリ・元の依頼・ユーザーが決めた事項を渡す。
5. 既存の文書を直すときは、その文書を最終の状態に書き換える。新しく書くときの保存先は、依頼で指定された場所、リポジトリの設計文書の置き場所の順に決め、書式もそこに揃える。どちらも無ければ、妥当なパスに保存して報告する。

## 書くこと

要る節だけを書き、該当しない節は見出しも作らない。

- 目的: 誰のどの問題を解くかと、それが解けたと分かる状態を数文で書く。
- 範囲: やることと、やらないこと。やらないことには、読み手が含まれると思いそうな隣の機能・画面・データを挙げる。後の変更に回すと合意した範囲があれば、それも書く。
- 要件: 利用者から見た振る舞いを、1 項目 1 つの振る舞いで番号を付けて書く。条件で結果が変わるものは「前提・操作・結果」で書く。異常系と境界は、どう振る舞うかに人の判断が要るもの (在庫が足りないときに注文を受けるか等) だけを書き、扱いが明らかなものは書かない。
- 業務のルール: 実装者がコードから決められず、人が決めるべきルールを書く。計算と端数の扱い、日付の区切りに使うタイムゾーン、誰が何をできるか (権限)、同じデータを 2 人が同時に変えたときにどちらを残すか、入力項目のうち業務上の意味がある必須・上限・既定値、既存データの扱い (移行) 等。
- 非機能要件: 外から合否を判定でき、受け入れの判定か設計の判断に要る条件だけを書く。合意済みか既存の契約で決まった値がある条件 (応答時間・同時利用数・保持期間等) は値と測り方を、値の無い条件 (オフラインで使える・データを端末の外に送らない等) は条件そのものを書く。
- 制約: 使わなければならないもの・使ってはいけないもの (技術・外部サービス・互換を保つ相手)、守るべき提供の順序やデータの保持期間と、その理由。
- 受け入れ条件: 要件の記述で合否が決まるものは繰り返さない。複数の要件をまたいで確かめること、合否を一意にするのに要る前提と観測する結果、測り方で合否が変わるときの測り方だけを、要件の番号を示して書く。
- 現状 (Design Doc): 変更に関わる既存の構成を、ファイルパスとモジュール名で示す。コードは貼らない。
- 設計 (Design Doc): 構成要素と責務、データの流れ、保存するデータとその関係、外部に公開する契約 (API・CLI・ファイル形式の名前・入出力と、契約として固定するエラー)。既存の契約やデータを変えるときは、それに依存する利用者・連携先と、保つものと変えるもの (互換・移行の要否) を書く。文章で追いにくい関係だけを Mermaid の図にする。
- 判断と理由 (Design Doc): 利用者への影響・外部との契約・構成を左右し、別の案もありうる判断ごとに、採った案・退けた案・理由を 1〜2 行で書く。
- 進め方 (Design Doc): 人が順序を決める必要があるときだけ書き、段階を依存の順に並べる。機能を段階ごとに提供するなら、各段階が入口から出口まで単独で動いて確かめられるように分け (画面から保存まで等)、満たす要件を番号で示す。データや契約を段階的に移行するなら、各段階で保つ互換と、次の段階へ進める条件を書く。
- リスクと戻し方 (Design Doc): 本番のデータや利用者に影響する変更だけ。何が起きうるかと、戻す方法。
- 仮定: 崩れると要件や設計が変わる前提を、根拠とともにレビューで否定できる形で書く。確かめられる前提は確かめてから書き、確かめられず判断が変わるものは未決事項にする。
- 未決事項: ユーザーの判断を待つ点を、選択肢と推奨とともに書く。実装に渡す版には残さない。

## 書かないこと

- 実装の詳細: 関数・クラス・変数の名前と分け方、使うライブラリの内部、テストケースの一覧。読み込み中・空状態の表示、タイムアウト、文字コード、並び順、ページ分割、再実行への耐性のように、エージェントがコードと規約から決める挙動。利用者や呼び出し元に見える結果 (失敗時に返すもの・一覧を全件で返すか分けて返すか等) を書くのは、依頼・既存の契約・業務のルールで固定する必要があるときと、新しく公開する契約として人が承認すべきときだけで、それを満たす内部の処理方式は書かない。
- 実装のコード (擬似コードを含む)。外部との契約を示す型・schema・入出力の例は書いてよい。
- リポジトリの AGENTS.md・rule・既存の文書が既に決めていること。必要なら参照する。
- 作業の進め方: ブランチ・commit・PR・レビューの手順・進捗の報告・日程。
- 実装に効かない企画の資料: ペルソナ・KPI・優先度の分類表・ワイヤーフレーム。依頼されたときだけ書く。
- 一般論・意気込み・作成の経緯・検討の過程。

## 書き方

- 結論から書く。1 つの節に 1 つの話題を書き、箇条書きを基本にする。表は同じ項目を持つものを並べるときだけ使う。
- 「適切に」「なるべく」「高速に」「など」のように読み手で解釈が分かれる語は、条件・数値・列挙に置き換える。列挙を「等」で閉じるときは、何が含まれるかの基準を添える。
- 「〜する」(必須) と「〜してよい」(任意) を書き分ける。
- 会話・口頭の合意・読み手が見られない資料を前提にせず、判断に要る背景は文書の中に書く。
- 同じものは同じ語で呼ぶ。リポジトリや業務に固有の語と略語は、初出で一言説明する。用語集は、固有の語が多いときだけ作る。
- 例の値は `<tenant_id>` のような placeholder で書く。架空の値も開発中の実際の値も、実装にそのまま写される。契約で決まった固定値は、例ではなく本文に書く。
- 長さは、レビューする人が一度に読み通せる量に収める。収まらないときは重複と要らない節を削り、それでも収まらなければ文書を分ける (実装の範囲は削らない)。

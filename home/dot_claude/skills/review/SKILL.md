# コードレビュー

作業ツリーの未 commit の変更 (unstaged・staged の変更と untracked の新規ファイル)、それが無ければ base ブランチとの差分、または指定された PR をレビューする。ソースや追跡ファイルは編集しない (PR へのコメント投稿は、依頼されたときだけ Step 4 で行う)。

lint / test 等の検証は、レビュー対象のファイルを書き換えない形で実行する。書き換えは未 commit の変更に混ざり、後から切り分けられないため。formatter や lint は、タスクや hook から呼ぶものも含めて check のモード (`--check` 等。`--fix` は付けない) か使い捨てのコピーで回し、どちらもできない検査は実行しなかったと報告する。キャッシュ・ビルド出力ができるのは想定内とし、それでも追跡ファイルが変わったら報告する。検査は対象のコードを実行するので、出所を信頼できると確かめられたコード (ユーザー自身の作業ツリー、リポジトリに書き込み権限を持つ人の PR 等) にだけ回し、外部の contributor の fork PR など確かめられないものは回さずに理由を報告する。

## Step 1: 変更の取得

1. 中身を出さずにパスを把握する: `git status --short` (untracked の新規ファイルを含む)、`git diff HEAD --stat`、`git diff HEAD --name-only` (PR は `gh pr diff <pr> --name-only`)。`git diff` だけでは staged の変更が漏れるので、`HEAD` と比べる。
2. 中身を出す前に secret ファイル (AGENTS.md「安全」の定義) を判定する。出力した secret は取り消せないため。rename は `git diff HEAD --name-status -M` で元と先の両方のパスを見て、片方でも secret なら両方を secret として扱う (`--name-only` には元のパスが出ない)。secret ファイルは中身を出さず、変更の有無だけを見る。
3. 差分本体を、secret ファイルを除いて取得する (`git diff HEAD -- ':(top)' ':(top,exclude)<path>'`。`:(top)` は、サブディレクトリから実行しても対象をリポジトリ全体にし、除外のパスを `--name-status` が出すリポジトリ root からのパスで解釈させる)。untracked の新規ファイルは、secret でないものの中身を読む (`?? <dir>/` は `git ls-files --others --exclude-standard -- <dir>` でファイルに展開してから判定する)。

レビュー対象が PR 番号 / URL で指定されたときは、代わりに次の手順で取得する。

- `gh pr view <pr> --json body,baseRefName,headRefOid` で説明・base のブランチ名・head の SHA (`<headRefOid>`) を取る。以降の secret の判定・差分・ファイルの読解・Step 4 の投稿は、すべてこの SHA に対して行う。
- head の commit が手元に無ければ `git fetch origin <base> pull/<pr>/head` で取る。比較の起点は `git merge-base origin/<base> <headRefOid>` の SHA (`<merge-base>`) で一度決め、`git diff --name-status -M <merge-base> <headRefOid>` で secret を判定してから、同じ 2 つの SHA で `git diff <merge-base> <headRefOid> -- ':(top)' ':(top,exclude)<path>'` の差分を取る。ファイルは `git show <headRefOid>:<path>` で読む (作業ツリーの内容と行番号は PR と食い違いうる)。
- fetch できないとき (read-only の sandbox 等)・PR が作業ツリーとは別のリポジトリのものであるとき・PR が merge 済みのとき (base が head を含むので、上の比較は空になる) は、secret を `gh api repos/<owner>/<repo>/pulls/<pr>/files --paginate --jq '.[] | [.filename, .previous_filename]'` で rename の元のパスも含めて判定し (`gh pr diff --name-only` には元のパスが出ない)、`gh pr diff <pr> --exclude '<secret>'` で差分を取り、ファイルは `gh api -H 'Accept: application/vnd.github.raw+json' 'repos/<owner>/<repo>/contents/<path>?ref=<headRefOid>'` で読む。この経路は SHA を固定できないので、判定の直前と差分の取得の直後に `gh pr view <pr> --json headRefOid` が `<headRefOid>` と同じことを確かめ、変わっていれば新しい head で判定からやり直す。
- lint / test は、作業ツリーが `<headRefOid>` で未 commit の変更も無いときだけ回す。それ以外では、作業ツリーで回しても PR の結果にならないので回さず、実行しなかったと報告する。

未 commit の変更が無ければ、base ブランチとの差分を対象にし、手順 1〜3 と同じく `git diff --name-status -M origin/<base>...HEAD` で secret を判定してから `git diff origin/<base>...HEAD -- ':(top)' ':(top,exclude)<path>'` で取得する。three-dot にするのは、merge-base から比べて base 側だけで進んだ変更を混ぜないため。`origin/<base>` は呼び出し元が指定した base で、指定が無ければ現在のブランチの PR の base (`gh pr view --json baseRefName`)、PR も無ければ `origin/HEAD` を使う。どちらの差分も無ければ、レビュー対象を確認事項として呼び出し元に返す。

## Step 2: レビュー

1. まず変更の全体像と意図をつかむ。必要なら関連ファイルも読む。
2. 各ファイルの変更と、変更が影響する経路 (変更していない呼び出し元・保存済みのデータ・設定) を、以下の観点のうち変更に関係するもので精査する。どの観点も、具体的な関数・経路と、そこに来る入力や状態に当てて確かめる。設定・指示文・ファイル配置の変更では、それを読む利用者やエージェントと、それが動く権限や前提に当てる (「バグが無いか」「きれいか」のような観点名だけで見ると、指摘が一般論になり、具体的な不具合を見落とすため)。観点は例で網羅ではないので、変更の性質から要る観点は足す:
   - 正確性:
     - 契約や実際の入力で意味のある境界の値 (0・空・1 件・上限ちょうど・上限を 1 超えた値・欠落した値等) で、変更した処理を追う。
     - 変更していない呼び出し元 (公開した API・CLI のリポジトリの外の利用者を含む) が、新しい戻り値・例外・引数を正しく扱えるか。
     - 保持すべき既存のデータが、必要な移行を経て変更後も使えるか。デプロイ中に新旧の版が同じデータを使うなら、互いが書いたデータを読め、更新するときに相手が書いた値を落とさないか。
   - テスト:
     - 変更した振る舞いと失敗の経路を、テストが実際に通り、守るべき結果や状態が崩れれば assertion が失敗するか (mock や stub がその経路を飛ばし、壊れても通るものになっていないか)。検証の漏れは、契約が破れたときの利用者への影響、既存のテストで検出できるか、テストを足すコスト (作成・実行・保守) で重みを付けて挙げる。
     - テストのレベルと契約の基準: テストは、利用者が呼ぶのと同じ公開 API から実際のコードを動かし、契約を assert する。公開 API は、application なら利用者がサポートされた方法で呼ぶ入口 (HTTP・RPC の endpoint・CLI・UI・worker が読む queue 等)、ライブラリなら文書・宣言した export・公開範囲の規約が示す利用者向けの API。契約は、要件・仕様・文書が保証することと、リポジトリの外を含む既存の利用者が依存すること。
     - この基準から外れ、要件を変えないリファクタ・バグ修正・機能追加で落ちるテストや、守るものの無いテストになっていないか:
       - 内部の module・class・関数を直接呼ぶテストを、明確な理由なく書いている。理由になるのは、ユーザーがそのレベルのテストを明示的に求めたこと、対象が今のコードの分け方に依らず要件に効く独自の仕様 (algorithm・定まった形式の parser 等) を持ち、公開 API ではそのケースを作るコストが高いか保証する結果が観測できないこと、テストのレベルを任されたときに、テスト内の準備 (CLI を subprocess で起動する等) でも公開 API を呼べず、契約を確かめられる最も上の境界で書いて未検証の経路を報告していること。依頼でテストのレベルが指定されたかが分からなければ、指定があればレベル自体は妥当という条件を添えて挙げる。
       - 契約のどの部分も守らないテストや、既存のテストが同じ入口と条件で既に検出するケースを足している。
       - 内部の呼び出しの順番・ログの文言・結果の並び・test double が受ける引数や回数を、契約が保証する範囲を超えて assert している。
       - 内部の helper を patch して条件を作っている。
       - 足したテストを、入口・機能 (理由のある下位のテストは部品) ではなく source の module の構成に合わせて置いているか、内部のコードの移動だけを理由にテストを動かしている (runner の探索と言語の制約が求める配置は除く)。
     - 利用者が依存するかで上の判定が変わるのに、仕様・文書・呼び出し元から判定できないものは、確認事項として挙げる。
     - 既存のテストを書き換えた差分では、元のテストが作っていた条件 (入力・事前の状態・依存先の失敗) と、それに対する契約上の結果の検査が失われていないか。
   - 失敗の扱い:
     - 失敗が呼び出し元や利用者に伝わらなくなる箇所 (空の catch・ログだけで続行・扱えない例外まで捕まえる広い catch・エラーを既定値や空の結果に置き換える・エラーの戻り値や Promise を捨てる)。フォールバックや別の層で失敗を扱う経路は、呼び出し元に返る結果と残る状態が契約に合うかで判定する。
     - 状態を変える経路で、一緒に成功すべき更新が途中の失敗で一部だけ残らないか (部分的な成功を許す処理は、どこまで成功したかを返すか)、契約が同じ操作の再送とみなすもの (再試行・二重送信・再配信) で効果が二重にならないか、同時に更新したときに守るべき条件が崩れたり片方の更新が黙って失われたりしないか。
   - セキュリティ (入力): 信頼できない値を、受け取る境界から使う箇所 (SQL・shell・ファイルパス・HTML) まで追い、その用途に合った防護 (パラメータ化・引数の配列渡し・パスの正規化と範囲の確認・エスケープ) が効いているか。外部のデータや LLM の出力が副作用 (コマンドの実行・ファイルの書き込み・外部への送信) につながる経路では、実行の前に、許す操作と対象・引数の制約がその経路で (ハーネスの権限設定かコードで) 強制されているか。
   - セキュリティ (権限と開示): 認可が、信頼できる側で呼び出し主体・操作・対象のリソースを確かめ、一覧・検索・集計では取得や集計に使うデータを許された範囲に絞り、判定できないときは拒否するか (同じ信頼境界の共通の層が全経路で同じ条件を確かめていれば、その境界では重ねなくてよい。別の層に意図して置いた防御 (DB の行レベルのセキュリティ等) は外さない)。secret がログ・エラー・応答に出ないか。
   - 性能 (どれも、実際に来うる件数と既存の上限・期限で効くかを判定する):
     - 件数に比例して増える不要なクエリ・API 呼び出し (ループの中の 1 件ずつの取得、N+1) と、ループの各回で同じ一覧を走査し直す処理。
     - 取得から出力までに一度に保持する量が、データの量とともに上限なく増える処理。全件を返す契約で、運用上ありうる件数やサイズで保持する量が問題になるなら、契約 (全件を確かめてから返す等) を保てる範囲で、分けて処理し、分けた分を順に書き出しているかを見る。
     - 完了を前提とするネットワーク呼び出し (HTTP・DB) と、有限の時間で終わる必要があり、止まると利用者や後続の処理を塞ぐ子プロセスで、クライアントの設定や呼び出し元の期限を含めても待ち時間全体に上限が無いもの。
   - 可読性: 分岐を追いにくい深いネスト (早期 return で浅くできるもの)、意味や単位がコードから読めない数値・文字列、隣接するコードの語や対の語とずれた命名。修正案は、挙動を保ったまま読みやすくなるときだけ出す。
   - 保守性: 同じ仕様を表すロジックや値が複数箇所にあり、片方だけ直すと食い違うもの (共通化の基準は AGENTS.md「コード」)。1 つの関数が、別々の理由で変わる複数の責務 (フラグで切り替える別々の操作等) を抱えている箇所 (分けると読みやすく変えやすくなるときだけ挙げる。分けすぎの基準は AGENTS.md「コード」)。
   - 設計・必要性: 過剰設計 (現に要求されていない抽象・汎用化・互換レイヤー、存在意義を一文で説明できない class)、現実に起こり得ない事象への防護コード・validation、デッドコード、テストを通すためだけの本番コード、標準ライブラリや既存の依存で同じくらい簡潔に書けるのに足した依存、責務の誤配置 (呼び出し先の都合の前処理を呼び出し元がしている等)
   - 方針: 変更を入れること自体が妥当か。変更前の実装と比べ、入れない・既存の仕組みに委ねる選択肢や、柔軟性・性能・運用の劣化を判定する
   - 回帰: 変更前と比べて劣化した点 (性能・出力品質・ツールの本質的な機能・read-only や tool 制限等の既存規約)。以前の方が良かった箇所は取り込み候補として個別に挙げる
   - 利用者の立場: 成果物を使う当事者 (エンドユーザー・運用者・依頼文が示す立場) の目で見て品質が足りているか
   - コメント・説明: AGENTS.md「コード」の基準に合わないコメント・docstring・description (コードの言い換え・開発の過程・今のコードが扱わない対象)、実装と一致しないもの
   - 指示への忠実さ (依頼文や PR の目的が示されたとき): 指示通りか、対応漏れ・スコープ外の変更 (目的に無い機能・オプション・設定項目を含む) が無いか
3. PR 本文や報告のテスト結果 (件数・カバレッジ) は自分で実行して照合できた場合だけ確認済みとする。
4. 2 つの PR・設計・実装の比較を求められたときは、違いだけでなく、共通点、旧版 (比較元) が優れていた点、デグレになる点も対称に挙げる。

## Step 3: 出力フォーマット

冒頭に総評を 1-2 文で書き、続けて各指摘に通番を付け、以下の形式で報告する:

### N. [Critical / Major / Minor / Nit] 指摘タイトル
- ファイル: `path/to/file:行番号`
- 確度: High / Medium / Low と検証方法 (実行して確認 / 読解のみ)。根拠にしたコードの挙動・実行結果・文書や仕様の記述を一言添える
- 問題: 何が問題か。どの入力・状況で何が起き、どう困るかを具体的に書く
- 修正案: どう修正すべきか (コード例があれば含める)

最後に、確認して問題なしと判断した観点と、判断に影響する未確認の事項 (実行できなかった経路・読めなかったファイル等) を列挙する。指摘がなければ、確認した範囲と安全と判断した根拠を述べる。

## Step 4: PR へのレビューコメント投稿 (依頼されたときだけ)

- 投稿の前と文面を書き直した後に、各指摘の主張と修正案の両方を一次証拠 (コード・実行結果・公式ドキュメント) で裏取りし直す。誤り・不要な指摘・その分野の専門家から見て初歩的な指摘は投稿せず、計測できる懸念は計測してから書く。
- 既定では pending (draft) review として作り、submit しない。ユーザーが最終確認してから submit するためで、submit まで明示的に依頼されたときだけ submit する。`gh pr review` は pending を作れず、実行した時点で submit される。pending review を作る tool が無ければ、GitHub の review 作成 API (`gh api` で `POST repos/<owner>/<repo>/pulls/<pr>/reviews`。`<owner>/<repo>` は PR のあるリポジトリ) を `event` を付けずに呼ぶ (`event` が無いと PENDING になる)。`commit_id` にはレビューした head の SHA を渡し、作る前に PR の head がその SHA から動いていないことを確かめる (動いていれば差分を取り直して所見を確かめ直す)。`commit_id` を省くと、コメントは投稿時点の head に付く。
- 各コメントは該当する file:line に付け、他のコメントを参照せずに単独で読めるように、何が問題か、放置すると何が困るか、どう直すかを書く。差分の外の箇所に影響する指摘は、原因になった差分の行に付けて影響する箇所を本文に書き、付けられる行が無ければ総評の中に同じ形で書く。
- コメントの冒頭の 1〜2 文で、どの条件で何が起きて何が困るかと、どう直すかが分かるようにし、それを裏付ける詳細 (再現の手順・長いコード例・調べた根拠) が数行を超えるときは `<details>` に折りたたむ (`<summary>` に中身を書き、`</summary>` の後と `</details>` の前後に空行を入れる。空行が無いと、折りたたみの中と後の Markdown が表示されない)。読む人が要点を先に判断でき、詳細は要るときだけ開けば済むようにするため。
- review の本文 (総評) は、冒頭に結論・判断が要る論点・判断に影響する未確認の事項を書き、行に付けたコメントの中身は繰り返さない。
- 強さのラベル (must / IMO / nits 等) は重大度と、そのリポジトリ・その PR の既存コメントの流儀に合わせる。PR が持ち込んだ回帰か、PR 以前からある問題かを区別して書く。
- 投稿後は、投稿したコメントの一覧 (file:line と要旨) と、review が pending のままか submit 済みかを報告する。

# Tests

- Contract: Choose the unit under test by responsibility (a module, class or application), not by how many places call a function, and test it through its interface: the functions and methods it provides to code outside it, or an application's CLI, HTTP endpoint or other entry point. Its contract is what the specification and documentation guarantee and what existing callers, external users of a public interface included, depend on. Assert the results that contract covers, such as return values, errors, output, the state the unit leaves and the side effects it specifies, and drive the unit through the interface and existing dependency boundaries rather than by patching its internals. Do not assert details the contract leaves open (internal call order, exact log text, the order of elements in an unordered result), because such tests fail on changes that keep the behavior. Call a helper inside the unit directly from a test only when the helper has a specification of its own that does not depend on how the unit is currently split into functions (e.g. an algorithm or a parser of a defined format), and its cases are impractical to set up through the unit's interface.
- Implementation-dependent tests: When a test fails because it depends on implementation details although the behavior it protects still holds, and the rules for editing existing tests (AGENTS.md and the skill in use) allow you to edit it:
  - Find the behavior the test protects and make its assertions, inputs, fixtures and doubles check that behavior through the interface, instead of making the test follow the current internals. The rewritten test must still set up the same condition in contract terms (the same input, prior state or dependency failure), not the same internal path, and keep every expected result in the contract the test checked, so that it fails when the contract breaks there; when checking through the interface would lose either, report it instead of rewriting.
  - Remove an assertion that protected nothing in the contract, since it tested only the implementation. Do not leave a test with no check: whether to remove such a test follows the rules for removing existing tests.
  - When a failing check asserts a detail the specification does not define, edit it only when you can confirm that users do not depend on it. If a caller or documented usage relies on it, treat the failure as a behavior change and report it; if you cannot tell (e.g. the interface is used outside the repository), report it as an open question without editing the check.
- Coverage: When asked to write tests, cover normal, error and boundary cases of the contract; do not test unreachable branches. Where the project can run property-based tests (see below), use them for behavior the specification guarantees for every input in a domain (e.g. a lossless round trip, an invariant the output keeps, agreement with a simpler reference implementation), unless example cases already cover every input. Use example-based tests for behavior the specification defines for particular inputs or situations, and keep boundary cases and counterexamples found earlier (by a generator or a bug report) as fixed cases that the usual test command runs every time, even when a property covers them, instead of depending on what the generator draws. A fixed input attached to the property (an explicit example or seed the framework runs with it) counts when the property's assertions are enough for it and the usual test command runs it through those assertions.
- Property-based tests:
  - Generate the inputs each property covers across the range the specification allows rather than a convenient subset (when the range is unbounded, keep sizes practical without losing its boundaries), including the inputs the code must reject when the property is about rejection, and make the generator produce the input shapes the property depends on (e.g. duplicates, empty and extreme values, related fields), which drawing values independently rarely hits. Prefer generating inputs inside the property directly to discarding the others. Discard a generated input only when the specification puts it outside the property, deciding that from the input itself, not from the result of the code under test or with the validation logic it uses, and run the assertions on every other input: discarding can drop exactly the inputs that trigger a bug. Discard through the framework's per-input mechanism (an assume-style call that marks the input invalid, or a generator filter), not an early return, which counts the input as passed, or a skip that ends the whole test.
  - Make sure the tests together would fail on plausible wrong implementations. A property that checks only a weak consequence passes broken code: a sort test that checks only the length passes an implementation that returns its input unchanged, so also check the order and that each element occurs as many times as in the input before the call.
  - Write a property-based test only with a library or standard tooling the project already has, and only when the project's usual verification (the test command its CI or documented workflow runs) will generate inputs for it, as is or once the test is registered where that setup expects, judged from the project's dependencies and test configuration; some tools run only stored seeds unless invoked in a fuzzing mode. Otherwise write the requested tests as example-based tests, and if the requested behavior has properties worth checking, propose adding the missing tool or command instead of adding it on your own.
  - After writing a property-based test, run it the way the usual verification does and confirm that the kinds of generated inputs the property targets reach the assertions, not only a few that survive discarding, with the tool's statistics, or with a temporary check when they do not show it. When the environment prevents that run or neither can show it, report it as unverified instead of replacing the test.
- Names: Within the project's naming convention, name each test (or table case / subtest) after the behavior it checks: the condition and the expected outcome in the specification's terms, so the names read as what the code under test must do. Do not name it after the function or the implementation steps.
- Isolation: Run against temporary directories and fixtures; never write to real data in the repository or to production output locations. In a property-based test, start each input, generated or fixed, from a fresh copy of the mutable state that affects its result and leave nothing it changed behind, instead of setting up state once per test function (e.g. in a fixture scoped to the test function).
- Regression Tests: When asked to add a test for a bug fix, confirm that it fails on the code before the fix because of the bug (not because of an import or fixture error) and passes after the fix; a test that passes either way does not detect the bug.
- Test Doubles: Run the code under test for real. Replace a dependency with a fake or mock only where the real one cannot be controlled, must not be reached, or cannot safely produce the condition under test (external services, the clock, randomness, a dependency's failure), and replace it at an existing boundary. Assert whether, how often, in what order and with what arguments a double is called only as far as the contract includes it (e.g. a request that must or must not reach an external service). Fix the time and random values an assertion depends on, except those a property-based or generated-input test generates as inputs; for those tests, make failing inputs reproducible.

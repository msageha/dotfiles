# LLM Agent Instruction Files (CLAUDE.md / AGENTS.md / rules / skills / agents / prompt assets)

- Budget: Always-loaded files (CLAUDE.md, AGENTS.md, rules without `paths`) are read on every session of every consumer that loads them, including subagent spawns, so the combined set must stay short; move procedures, reference tables and checklists into skills or reference files that are read only when needed. Grok, when its Claude compatibility for rules (`compat.claude.rules`) is on, ignores `paths` and loads every rule in `~/.claude/rules` on every session, so a path-scoped rule still costs context there. Antigravity truncates each rule file, including the global AGENTS.md, at 24,000 bytes measured after includes are expanded (UTF-8, so roughly 8,000 Japanese characters), and drops everything past that point.
- Progressive disclosure: Multi-file procedures (custom skills, multi-stage agent designs) load each file at the step that needs it, never all files up front. Keep reference files one level below SKILL.md and state for each what it contains and when to read it.
- Consolidation: Keep prompts, and any definition or mapping table that prompts and scripts share, in one asset per scope (AGENTS.md, a skill, or a machine-readable md / csv that the prompt references) with the actual values, instead of scattering or duplicating them across code and several assets, so that everything the agent receives can be read in one place.
- Reader: The reader is an LLM. Prefer short bullets; use a table only when rows are genuinely comparable records. Write each rule as a plain sentence without emphasis (IMPORTANT, CRITICAL, MUST, bold, ALL CAPS), which current models over-apply, and add a short reason when a rule's purpose is not obvious so the reader can apply it to adjacent cases. Treat lists of rules, viewpoints or checklist items as examples and aids, not as the coverage itself: a reader that only follows the list misses whatever the list omits, so state the principle and its reason and leave the reader to examine the task from several viewpoints, including ones the list does not name.
- Examples and goals: Check that no example or example value can mislead the reader (for instance by being copied verbatim), and write variable parts with one consistent placeholder style such as `<name>`. Say what to do, not only what to avoid. State a goal as a relative direction paired with a stopping condition (e.g. "halve the runtime; stop when an attempt no longer improves it") rather than a fixed value taken from the current state.
- Harness: Do not restate what tool definitions or the harness already provide (tool descriptions, default behaviour, MCP server instructions). Write only the "when to use" that they do not contain. In a file several tools read (AGENTS.md, skill bodies included into other tools), judge per consumer: drop content only when every consumer already gets it, and move content that only one consumer needs into that tool's own instructions file.
- Capability over instruction: To keep an agent away from dangerous operations, remove the capability instead of relying on "do not" instructions; prompt injection can defeat an instruction but not a missing capability. Claude Code enforces a subagent's `tools` / `disallowedTools`; Codex (0.166) custom agent files cannot override the parent's `sandbox_mode`, `approval_policy`, `model_provider` or `mcp_servers`; subagents inherit them. A skill's `allowed-tools` / `disallowed-tools` last only for the turn that invoked the skill (`allowed-tools` only pre-approves and never restricts unlisted tools), and other tools reading the same SKILL.md cannot be relied on to honour `disallowed-tools` (Codex ignores it; Antigravity and Grok do not document it). Bash left available keeps write capability whatever the Edit / Write restrictions say. Put a lasting restriction in the harness's permission settings (Claude `permissions.deny`, Codex `rules/*.rules`) or the sandbox. Because `allowed-tools` widens permission for that turn, list only the specific patterns the skill's procedure runs (e.g. `Bash(gh pr view:*)`), and do not pre-approve bare `Bash`, `Write` or `Edit` in a model-invocable skill that reads external content such as emails, PR comments or web pages.
- Grounding: Add or change a rule only on the basis of the user's actual instruction history or official documentation, never on speculation.
- Research: Before writing a new skill or agent definition, survey the reference implementations the user names, the harness vendors' official skills repositories (e.g. anthropics/skills, openai/skills), and current primary sources for the domain (e.g. OWASP for security assets).
- Preservation: What a rewrite must keep is the behaviour that norms from the user's instruction history produce, not their wording; moving such a norm to the file or section that owns its topic is fine. Treat every revision as including deletion: list as candidates for removal the norms grounded in neither the user's history nor official documentation, norms that follow from a principle already stated, and norms for what current models do by default. Fix stale, duplicated or factually wrong text instead of preserving it; length is not something to preserve.
- Placement: When adding to an existing instruction file, put the new rule under the section that already owns that topic instead of appending a new section or a trailing list.
- Scope: User-scope skills and agents (`~/.claude/`, `~/.agents/`, `~/.codex/`, `~/.gemini/config/`, `~/.grok/`) must not embed repository-specific knowledge; write only instructions that hold in any repository.
- Project scope: AGENTS.md, skills and agents inside a repository must describe that code's actual design, architecture and implementation as verified by reading it, and follow the target tool's current official guidance.
- Revision from runs: When revising a prompt from run results, locate the exact prompt text recorded in the execution logs that produced the defect instead of guessing which wording caused it. Run each change as an experiment: vary few factors at a time, compare across several targets and repeated runs, watch for regressions such as more failed or partial runs, and record the conditions and results, so that the prompt is not tuned to a single target.
- Target-agnostic: Prompt assets of an agent harness you build (its AGENTS.md, skills, agent prompts, prompts embedded in code, schema descriptions) must hold for any target repository: embed neither the harness's implementation details nor concrete values from a particular target, and do not assume the launched agent knows the harness exists. When target knowledge is needed, add or fix the preceding discovery step instead of hardcoding it. When you find one such leak, search the other assets for the same kind.
- Reader simulation: After writing or editing prompt assets, check them against each other for contradictions and confirm the task is achievable with only what the reader receives at runtime (its own files, tools and inputs), not with context only the author has. Whether a prompt tells the agent to ask or to decide on its own follows the one-shot worker / unattended loop distinction in AGENTS.md「委譲」.

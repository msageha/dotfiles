# ユーザーの既定の契約

次の点は、このユーザーの既定の契約として Codex の既定動作より優先する。その場でユーザーが明示的に別の指示をしたら、そちらに従う。作業規約の全体は AGENTS.md にある。

- 依頼か問いかは、語形ではなく、ユーザーが変更を求めているかで決める。説明・評価・原因・方法を求める問い (「〜ってなに？」「なんで〜したの？」「どう思う？」「〜すべき？」「〜の方法を教えて」) と、外部のサービスやユーザーの環境で実現できるかを確かめる問いには、コード・設定・git を含め状態を変えずに確かめて答える。ユーザーは評価を見てから採否を決める。具体的な変更を求める発話は、「〜できる？」「〜したいんだけどできる？」の形でも依頼として行い、できなければ理由を返す。
- 調査・原因分析・レビューだけの依頼は read-only で進め、所見と選択肢を示して指示を待つ。「確認して、問題があれば直して」のように直すところまで頼まれたら、直して検証まで行う。
- 調べても解消しない曖昧さで成果物の方向が実質的に変わる分岐 (アーキテクチャ・中核の処理の流れ・IAM や IaC の設計・大規模な構造変更) があれば、変更に着手する前に 1 回にまとめて確認し、待つ間も read-only の調査は進める。それ以外では、AGENTS.md「安全」節の操作と、AGENTS.md がほかに指示を求めるもの (今も残る挙動を確かめるテストの削除等) を除いて止まらない。
- 作業中の割り込みは元の作業の取り消しではない。質問・情報の追加・別の依頼には応えてから元の作業に戻り、訂正・範囲の変更は反映して続ける。頼んでいない工程への疑義 (「なんで〜してるの？」) は、その工程をやめて頼まれた操作を先に終える合図として扱う。答えて次の指示を待つのは、停止の指示と、作業の方向そのものへの異議のときだけ。
- commit・push・PR 作成・merge は、ユーザーが依頼ごとに明示したときだけ行い、前の依頼の許可は次へ持ち越さない。変更を始めるときの作業場所は、上から順に最初に当てはまるもので決める。(1) 今回の作業に属さない未 commit の変更がある: worktree。(2) base か merge 済みのブランチ (squash merge は PR の状態で判定) にいる: base を最新にしてから、依頼に合うブランチを checkout する。(3) 今回の作業のブランチにいるか、今回の作業の未 commit の変更がある: 今の checkout。(4) それ以外: worktree。worktree はこの条件のときだけ作り、委譲された側は渡された作業場所で作業する。PR は依頼されない限り draft にしない。

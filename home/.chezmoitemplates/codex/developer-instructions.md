# ユーザーの既定の契約

次の点は、このユーザーの既定の契約として Codex の既定動作より優先する。その場でユーザーが明示的に別の指示をしたら、そちらに従う。作業中のリポジトリの AGENTS.md / CLAUDE.md と食い違うときの扱いは、作業規約 (global の AGENTS.md) の前文に従う。作業規約の全体もそこにある。

- 依頼か問いかは、語形ではなく、ユーザーが変更を求めているかで決める。説明・評価・原因・方法を求める問い (「〜ってなに？」「なんで〜したの？」「どう思う？」「〜すべき？」「〜の方法を教えて」) と、外部のサービスやユーザーの環境で実現できるかを確かめる問いには、コード・設定・git を含め状態を変えずに確かめて答える。ユーザーは評価を見てから採否を決める。具体的な変更を求める発話は、「〜できる？」「〜したいんだけどできる？」「あなたが行える？」の形でも依頼として行い、できなければ理由を返す。問いと依頼が混ざれば、依頼を行い問いにも答える。
- 調査・原因分析・レビューの依頼は read-only で進め、所見と選択肢を返して指示を待つ。「確認して、問題があれば直して」なら直して検証まで行う。「問題なければ merge して」のような条件付きの依頼は、条件を判定して根拠を示し、指定の分岐まで進める。
- 確認は方針を決める前に 1 回にまとめる。確認するのは作業規約の「安全」節の操作と、調べても解消しない曖昧さで成果物の方向が実質的に変わる分岐 (アーキテクチャ・中核の処理の流れ・IAM や IaC の設計・大規模な構造変更) で、それ以外では、作業規約・rule・skill がほかに指示を求めるもの (今も残る挙動を確かめるテストの削除等) を除いて止まらない。選択肢にはラベルと推奨 1 つを付け、選んだときに何が変わるかと付随する判断 (積む先・PR の分け方等) を添えて、1 回の回答で最後まで進められる形にする。それ以外の可逆な判断は推奨で進めて報告に書く。確認を待つ間も read-only の調査は進める。
- 作業中の割り込みは元の作業の取り消しではない。質問・情報の追加・別の依頼には応えてから元の作業に戻り、訂正・範囲の変更は反映して続ける。頼んでいない工程への疑義 (「なんで〜してるの？」「今なにをやっているの？」) は、その工程をやめて頼まれた操作を先に終える合図として扱う。答えて次の指示を待つのは、停止の指示と、作業の方向そのものへの異議のときだけ。
- commit・push・PR 作成・merge・tag・issue の起票や close は、ユーザーが依頼ごとに明示したとき (作業規約の前文が認める常設の手順を含む) だけ、指示された段階まで行う。ファイルの変更の依頼は commit の許可ではなく、前の依頼の git の許可は次へ持ち越さない。PR は依頼されない限り draft にしない。
- 今回の作業に属さない未 commit の変更 (別のセッションと checkout を共有しているとき等) には、stash / checkout / reset で触れない。変更を始めるときの作業場所は、上から順に最初に当てはまるもので決め、worktree は確認を挟まずに作る。(1) 今回の作業に属さない未 commit の変更がある: worktree (今回の作業の変更が既にあれば、その hunk だけを写し、元の変更は消さずに報告する)。(2) base か merge 済みのブランチ (squash merge は PR の状態で判定) にいる: base を最新にしてから、依頼に合うブランチを checkout する (今回の作業の未 commit の変更は持ち越す)。(3) 今回の作業のブランチにいるか、今回の作業の未 commit の変更がある: 今の checkout で続ける。(4) それ以外 (merge されていない別のブランチ・detached HEAD 等): worktree。worktree はこの条件のときだけ、そのリポジトリの `.worktrees/<name>` に、依頼に合うブランチ (新規なら最新の `origin/<base>` から) で作り、作業用の clone は作らない。委譲された側は、渡された作業場所で作業する。

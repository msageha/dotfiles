# 委譲の手順

サブエージェント・バックグラウンドの worker・外部のエージェント CLI に依頼を出すときに読む。

- 委譲のプロンプトには、受け手が追加の調査なしに着手できる情報 (目的・対象・範囲外・前提・作業場所・編集してよいファイル・自分で実行した検証の結果・出力の形・完了条件) を入れる。結果を自分が受け取る依頼には、ほかのエージェントからの依頼であることと、結果を呼び出し元へ返せばよいことを書く (書かないと、受け手は自分をユーザーに成果物を返す側とみなし、相談・独立レビューを起こし直しうる)。相談・レビュー・調査だけを頼むときはその旨も書く。ユーザーが明示しない限り commit / push はさせない。
- レビュー・検証を頼むときは、変更の性質から選んだ観点を、対象の関数・経路と確かめる入力や状態に当てた形で書く (「<外部呼び出し> が失敗したときに、呼び出し元に返る結果と残る状態を確かめる」「<関数> に上限ちょうどの <入力> が来たときの結果を確かめる」等。観点の例は、review skill の SKILL.md を読める環境では、その Step 2 にある。skill として起動せず、ファイルとして読む)。独立した判定を頼むときの条件は、自分が不具合を見つけた入力ではなく、変更の契約から選ぶ (次項)。同意を求める問い (「問題ないよね？」「これで合ってる？」) と観点の無い依頼 (「バグが無いか確認して」「全体的に見て」) は使わない。受け手が同意か一般論だけを返しがちなため。
- 独立した判定を頼むときは、目的・差分と、変更の性質から選んだ観点を着手点として渡して関連の経路も見させ、自分の所見・疑い・暫定の結論と、それを示すために選んだ再現の条件や結果は書かない (受け手の探索を自分の見立てに狭めないため。lint / test のように変更全体に回した検証は、その成否を渡してよい)。自分が疑う不具合の再現の条件・ログは、独立した判定を受けた後に、その所見の再現を頼むときに渡す。
- レビューの結果は、所見を網羅して、箇所・起きる条件・影響・根拠 (根拠にしたコードの挙動・実行結果・文書や仕様の該当箇所と、実行して確かめたか読んだだけか)・修正案の形で返させ、指摘の有無にかかわらず、見た範囲と判断に影響する未確認の事項 (読めなかったファイル・実行できなかった経路) も返させる。検証の結果は、実行した条件・観測した結果・確かめていない範囲を返させる。
- 外部のエージェント CLI は、その CLI の sandbox と書き込みの範囲を保ったまま、承認や入力を待って止まらない設定で起動し、出力が進んでいるかを見ながら待つ。並列の worker には変更するファイルを重ならないよう割り当て、担当外の修正は報告させる。失敗した分は出し直して揃えてから統合し、止まった委譲は打ち切って小さく分けて出し直す。
- 履歴を持たず質問もできない受け手 (バックグラウンドの worker・非対話で起動した外部のエージェント CLI 等) には、確認を先に済ませ、結果の返し先を含めて渡す。一回限りの worker には、結果を大きく変える情報が足りなければ推測させず「確認事項」として返させる。無人で回り続けるループには問い合わせを求めず、迷う判断は自分で決めさせて置いた仮定を報告させる。
- ユーザーが改善を頼んだ指標 (CI・テスト・build の所要時間、レイテンシ、メモリ、サイズ等) を比べられる形で測れ、試す価値のある案が複数あり、改善するほど価値があるときは、受け手に改善を長く繰り返させる。依頼のうち不具合の解消や機能要件の充足で完了する部分と、数手で終わる改善には使わない。手順は次のとおり。
  - 目標: ユーザーが目標値を決めていればその値を使う。決めていなければ、着手時の実測とボトルネックの分析で見込める改善を全部入れても届きにくい値を置く。届きやすい目標では、受け手が最初の改善で止まって余地を残すため。届かないと見込んでいることは受け手に書かない (書くと受け手が早く切り上げる)。
  - 範囲: 目的・編集してよい範囲・変えてはいけないもの (実行する検査とテストの範囲・coverage・挙動・結果の正しさ・セキュリティの設定) は自分で決めて渡し、その中で何を試すかは受け手に選ばせる。届かない目標は検査を外して数値を作る圧力にもなるので、測り方を変える・検査を減らすことで得た改善は数えないと書く。追加の許可や確認が要る案 (権限・共有環境・設計の大きな変更) は、実行せずに理由を添えて返させる。
  - 測り方: コマンド・環境・キャッシュの状態・回数と集計と、改善とみなす差の下限 (変更前の状態を繰り返し測ったばらつきより大きくする) を自分で決めて渡す。各候補は直前に残した状態と比べさせ、互いに依存して単独では差が出ない変更はまとめて 1 つの候補として測らせる。共有の CI のように手元で測れない指標は、手元で測れる代わりの指標 (同じジョブを手元で実行した時間等) で候補を比べ、残す候補がまとまったら、許可を得て実環境で測って判定する (許可が無ければ、手元での前後の値と、実環境での達成は未確認であることを報告する)。着手時に、実行される検査の一覧 (テストの件数等) も記録しておく。
  - 受け手の試行: 試行ごとに測らせ、改善した変更だけを残させ、改善しなかった試行はその試行で加えた変更だけを戻させる。試したこと・測った値・残したか戻したかと、残した状態を復元できる形 (未追跡のファイルを含む差分等) は、作業対象の外の記録ファイルに書かせる。途中で止まっても、記録から戻して再開できるようにするため。
  - 受け手が返ったときの確認: 自分で同じ条件で測り直し、着手時に記録した検査の一覧と変更後の実行ログを照合し、差分から、テストの assertion・除外の設定・測定の経路を変えていないことも見て、検査の範囲と結果の正しさが保たれていることを確かめる (キャッシュを変えたなら、入力を変えたときに検査が走ることも)。確かめられなかった変更は、記録を使って最後に確かめた状態へ戻させる。
  - 打ち切り: 打ち切りの時間・試行の回数と、改善が何回続けて無ければ止めるかは、ユーザーの指定が無ければ自分で決めて最初の依頼に入れ、出し直しをまたいで通しで数える。受け手にも次の停止条件を渡し、当たったら返させる。期限は受け手が返らなくても自分で見て、過ぎたら止める。受け手が返るたびに、目標に届いた・打ち切りに達した・決めた回数続けて改善が無かった・権限や測定の手段が無くて続けられない、のどれかに当たれば止める。当たらなければ、測り直した値と目標との差を添えて続けさせる (続きを頼めない受け手なら、前の受け手が止まったことを確かめてから、記録ファイルを渡して出し直す)。
  - 報告: ユーザーへは、止めた理由・前後の測定値・目標との差・残した変更・戻した試行と、自分で決めた目標と上限ならその旨を書く。
